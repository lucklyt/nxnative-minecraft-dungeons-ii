# nxnative — Minecraft Dungeons II adaptation

This repository is an experimental adaptation of [seedds/nxnative](https://github.com/seedds/nxnative)
focused on **Minecraft Dungeons II**, title ID `0100A7C01B792000`, game version
**1.1.3.0**, on Apple Silicon Mac and iPhone. The inherited games gallery below
is upstream project information; other games have not been revalidated against
this branch's shared host changes.

## Player features

- **60 FPS target** on iPhone and Apple Silicon Mac, enabled automatically for
  the supported game version. Actual frame rate depends on the device and scene.
- **Sign in with your own Microsoft account** from the game's Settings.
- **Microsoft cloud-save synchronization:** access your account's cloud
  characters and upload progress through the game's normal save flow, including
  cloud saving for offline heroes when enabled in the game.
- **Automatic sign-in restoration** after restarting the app, while Microsoft
  authorization remains valid. Settings shows your account name and linked state.
- **Networking enabled by default:** no configuration-file editing is needed
  after installing a newly built app.

Start with the [build, sign-in and cloud-save guide](#build-sign-in-and-use-cloud-saves).
Bring your own game files and account; no personal saves or credentials are
included in this repository.

## Current support and limitations

The supported version is **1.1.3.0**. Mac gameplay and iPhone level-100 camp
play have been tested. Microsoft sign-in, cloud-character retrieval, progress
upload and sign-in restoration after two full app restarts passed iPhone tests.
Menu tests measured 60 FPS on both platforms; sustained iPhone combat performance
and complete rendering remain unverified. A 60 FPS target does not guarantee
60 FPS in every scene.

First-time users link their account in the game's Settings. Existing users
upgrading from an older build need one successful Settings login to enable
automatic restoration. Expired/revoked authorization, some login failure paths
and account unlinking need further testing. Multiplayer is unverified.
The tested Microsoft cloud-save path does not require a Nintendo account.

This is an experimental adaptation for this game. New game updates may require
updated patches; other games in the inherited upstream gallery have not been
revalidated against this fork.

## Implementation and validation

The [game-specific notes](dm/games/0100A7C01B792000/README.md) document the memory
adaptations, frame pacing, Microsoft authentication and cloud-upload fixes.
These changes are stored as source and game-profile data and apply automatically
when repacking the supported version. Shared host fixes may also affect other
games that use those paths.

Mac and signed iPhone builds passed, along with host tests, 46 ARM64 login-adapter
tests, 14 registry tests and four documentation tests. Original game uploads
returned HTTP 201 and completion status 200. The latest cross-game regression
attempt is blocked by missing locked Metal tools; it is not a cross-game
compatibility guarantee. See the game-specific notes for detailed evidence and
remaining validation gaps.

## Build, sign in and use cloud saves

These steps are for **Minecraft Dungeons II 1.1.3.0**, title ID
`0100A7C01B792000`. Use your own game files, keys, Apple signing account and
Microsoft account. The repository contains no game data, account tokens or
personal saves. The tested Microsoft-only path does not require supplying a
Nintendo account. Multiplayer is not validated.

### 1. Get this fork and prepare the game

On an Apple Silicon Mac, install Xcode and Homebrew, then run:

```sh
git clone https://github.com/lucklyt/nxnative-minecraft-dungeons-ii.git
cd nxnative-minecraft-dungeons-ii
brew install xcodegen zstd spirv-cross glslang
brew install --cask dotnet-sdk
python3 -m venv .venv
source .venv/bin/activate
python3 -m pip install lz4 capstone fonttools "backports.zstd; python_version < '3.14'"
```

If you already cloned this fork, run `git pull` before rebuilding. Put the base
game, the **1.1.3.0 update** and any DLC you own in one folder outside the
repository. Keep `prod.keys` outside the repository too. The packer selects the
newest update in that folder: do not include a newer, unvalidated update.
New versions may need updated build-specific patches even if packaging succeeds.

### 2. Rebuild and install

Run from the repository root, replacing the example paths with your own:

```sh
# Prepare the iPhone project, including this fork's game adaptations.
python3 scripts/build_ipa_from_nsp.py "/path/to/game-folder" -k "/path/to/prod.keys" --keep-extracted --prepare-xcode
```

Open the generated
`/path/to/game-folder/0100A7C01B792000_build/xcode/DmIOS.xcodeproj` in Xcode:

1. Sign in with your own Apple ID in Xcode Settings → Apple Accounts.
2. Select the **DmIOS** target → **Signing & Capabilities**, enable automatic
   signing, and select your own team. Use a unique bundle identifier if needed.
3. Connect and unlock the iPhone, trust the Mac and enable Developer Mode when
   requested. Select the actual iPhone as the run destination.
4. Select the game's scheme and press **Run**. If iOS asks, trust/verify your
   developer app in Settings → General → VPN & Device Management.

See [Xcode installation details](docs/development.md#build-and-run-on-a-device-with-xcode)
for signing and memory-capability requirements. Keep the same bundle identifier
when updating, and back up your saves before replacing an existing installation.

Alternatively, omit `--keep-extracted --prepare-xcode` to produce an unsigned IPA,
then sign and install it with your own sideloading tool. For a Mac app instead:

```sh
python3 scripts/build_ipa_from_nsp.py "/path/to/game-folder" -k "/path/to/prod.keys" --platform mac-app
```

Repacking from this fork applies the supported profile automatically; no manual
binary edits, debugger patches or another person's login cache are needed.

### 3. Start with networking already enabled

New builds from this fork **enable networking by default for this game**, on
both iPhone and Mac. Open the installed app normally; no file editing, launch
variable or extra switch is needed. Continue to the in-game account linking
step below. Enabling networking does not authorize an account by itself.

If upgrading an old installation, an existing explicit `DM_NETWORK=0` override
still keeps it offline. Remove that line from its `env.txt` (or change it to
`DM_NETWORK=1`) and fully restart the app. Old binaries must be rebuilt and
reinstalled to gain the new default; updating the README alone does not change
an installed app.

For optional offline use, set `DM_NETWORK=0` in the app's `env.txt` and restart:
on iPhone this is Files → On My iPhone → the game's folder, beside `save/` and
`log.txt`; on Mac it is
`~/Library/Application Support/nxnative/0100A7C01B792000/env.txt`.
This profile default does not enable networking for other games.

### 4. Link your own Microsoft account

1. Enter the game normally, then open the **in-game Settings** (not the
   nxnative launcher settings) and choose the Microsoft account Link action.
   First-time users initiate authorization here; merely opening the game does
   not link an account.
2. When the game displays a device code, open
   [Microsoft's authorization page](https://www.microsoft.com/link) on another
   device and enter the **currently displayed** code. Sign in with the Microsoft
   account whose cloud saves you want, and complete the authorization yourself.
   Never send a password, token or device code to the repository maintainers.
3. Keep the game in the foreground while authorization completes. A second
   device for the browser avoids interrupting the phone app during this step.
   If the code expires, restart the link operation and use the new code.
4. Wait for the game's account-linked success message and choose Continue.
   Settings should then show your account nickname and linked state.

After one successful login, subsequent full app restarts can restore the same
account through the genuine Microsoft authorization cache. Older installations
need one successful Settings login after upgrading to create the restore record.
Authorization can still expire or be revoked; automatic restoration is not a
replacement for Microsoft authorization.

### 5. Download and upload your cloud character

1. While signed in, open the game's cloud-save/character selection interface.
   Use the same Microsoft account that owns the existing cloud character.
   Check the **Offline Heroes** filter too: the tested cloud character belongs
   there, so an empty Online Heroes list alone does not mean login failed.
2. Select the intended cloud character and use the game's download/load action
   if offered. Enable the game's **cloud saving for offline heroes** option
   when using an offline hero. Labels may differ with the game's language.
3. Enter the character, play, then use **Save and Return to Main Menu** in the
   game's own menu. Leave the app online and in the foreground until its saving
   activity finishes; do not force-close it during upload.
4. To confirm synchronization, refresh/reopen the cloud list, or check the
   character's progress on another installation signed in to the same account.
   A cloud-list summary may remain unchanged even when the save payload updates.

Back up local saves before downloading over an existing character. Cloud saves
belong to your Microsoft account; rebuilding does not transfer someone else's
characters. The signed iPhone test restored a level-100 character and completed
an original game upload (HTTP 201, completion 200), including after two full
app restarts. Other devices/accounts still need their own validation.

### If something goes wrong

- **Link is disabled/offline:** use a newly rebuilt app from this fork, check
  for an old `DM_NETWORK=0` override, then fully close and reopen it.
- **Code expired or login appears stuck:** restart the app, return to Settings
  and start linking again. Use the latest code and keep the app foregrounded.
- **No cloud characters:** confirm the account, offline/online character filter
  and cloud-save option before replacing any local save.
- **Still failing:** collect the app's `log.txt` (and `log.prev.txt` for the
  preceding run), game version, device/iOS version and the visible error.
  Review logs for personal information before sharing. Live Settings failures,
  revoked-token recovery and Unlink still have validation gaps; see the
  [game-specific notes](dm/games/0100A7C01B792000/README.md#reproducing-this-build).

## Upstream nxnative overview

Play your own Nintendo Switch games natively on iPhone and iPad. Bring your game (its NSP files) and your `prod.keys`; one script turns them into an IPA that you sideload.

It is not an emulator: the game's own code runs directly on the Apple chip, with Switch graphics rebuilt on Metal. Nothing from any game is in this repository, and the project is not affiliated with Nintendo or any game publisher.

This project is built on other people's work:

- **[d2r-mobile](https://github.com/jhaizhou-ops/d2r-mobile)** (MIT) developed this native-execution approach, for Diablo II: Resurrected. nxnative started as a copy of its generic parts: the NSO rewriter, the host that stands in for Horizon, the NVN-on-Metal layer and the iOS app shell. Fixes go both ways.
- **Ryujinx** (MIT): its shader translator (`Ryujinx.Graphics.Shader`, `Ryujinx.Common` and `Spv.Generator` 1.3.2, in `dm/third_party/ryujinx` with a few fixes listed in [its README](dm/third_party/ryujinx/README.md)) turns the games' Maxwell shaders into SPIR-V. Its emulation of the kernel and system services is also a reference when the host's behaviour is in doubt.
- **[Atmosphère](https://github.com/Atmosphere-NX/Atmosphere)**: its kernel, mesosphère, is the reference for Horizon's synchronization semantics (address arbiter, condition variables).
- **yuzu**: Maxwell instruction encodings for the shader reference tool, and a cross-check for kernel behaviour.
- **[LibHac](https://github.com/Thealexbarney/LibHac)**: reads NSPs and layers updates over the base game in `dm/tools/nx_extract`. **hactool** did the first extractions.
- **[SPIRV-Cross](https://github.com/KhronosGroup/SPIRV-Cross)**: SPIR-V to Metal Shading Language. **[glslang](https://github.com/KhronosGroup/glslang)** compiles the GLSL of OpenGL games to SPIR-V for it.
- **deko3d** (zlib): its texture layout size algorithm is ported in `dm/gfx/nvn/nvn_tex.c`.
- **libvpx** (VP9 movies), **stb_vorbis** (movie sound), the **Vulkan headers** and **NVIDIA FLIP** ship in `dm/third_party` with their licenses ([list](dm/third_party/README.md)).
- **Capstone**, **lz4**, **fontTools** and **XcodeGen** are used by the build.

## Pack an IPA

Prefer a graphical interface to the command line? **[NX2Apple](https://github.com/LNPANDY/NX2Apple)** is a community fork with a macOS app that runs this whole pipeline for you and packs the game files into a sharded RomFS archive for a slimmer IPA. It is a separate project that follows this one; the steps below are nxnative's own command-line way.

**1. Get nxnative and its tools** (once, on a Mac with [Xcode](https://apps.apple.com/app/xcode/id497799835) and [Homebrew](https://brew.sh)):

```
git clone https://github.com/lucklyt/nxnative-minecraft-dungeons-ii.git && cd nxnative-minecraft-dungeons-ii
brew install xcodegen zstd spirv-cross glslang
brew install --cask dotnet-sdk
python3 -m pip install lz4 capstone fonttools "backports.zstd; python_version < '3.14'"
```

**2. Put one game's NSPs in a folder**: the base game (an NSP, or an XCI cartridge dump), plus its update and DLC if you have them:

```
~/Games/MarioWonder/
  Super Mario Bros. Wonder [010015100B514000][v0].nsp
  Super Mario Bros. Wonder [010015100B514800][v327680].nsp
```

NSZ and XCZ files (compressed NSPs and XCIs) work too: the script converts them once with [nsz](https://github.com/nicoboss/nsz) (`python3 -m pip install nsz`) and keeps the NSPs in `<title ID>_build/nsp/`, which takes their full size on disk.

Any version works, with or without an update: the script packs the newest version in the folder. DLC is optional too: the DLC in the folder is packed, and without it the game sees none, as on a Switch without it. Each game was tested on one version (an update named in the table above is the one its 60 fps needs). With another version the script builds the game with that version's own shaders and says that the version was not tested; fixes made for the tested version's code, such as the 60 fps ones, don't apply to it.

**3. Run the script:**

```
python3 scripts/build_ipa_from_nsp.py ~/Games/MarioWonder -k ~/keys/prod.keys
```

The IPA appears in the same folder (here `~/Games/MarioWonder/SMBWMobile.ipa`). The first build takes 30–60 minutes. A later one reuses every step whose inputs did not change, so after a pull that changes only the host it takes about a minute. The small `.idx` file beside the IPA (`.app.key` beside a Mac app) records what was packed; keep it for the next build. You need free disk space of about twice the NSPs' size plus 10 GB. Options such as `-o` (output path) and `--app-name` are listed by `-h`.

**4. Install** the IPA with your sideloading tool (AltStore, Sideloadly, LiveContainer, …). The app gets the game's name, icon and version (the update's version, for example 1.2.1 for Mario Wonder; the base game's when there is no update). Sign it with the **Increased Memory Limit** capability (`com.apple.developer.kernel.increased-memory-limit`) if your tool can: without it iOS gives the app about 3.4 GB and closes the bigger games (Hyrule Warriors: Age of Calamity and Hades II use more, Breath of the Wild and Cuphead come close); with it a recent iPhone gives about 6 GB.

To play on a Mac with Apple silicon instead, `--platform mac-app` packs a Mac app of the game that you open from Finder ([A Mac app](docs/development.md#a-mac-app)).

With an Apple developer account you can instead build and install from Xcode: `--prepare-xcode` makes an Xcode project for the game rather than an IPA ([Build and run on a device with Xcode](docs/development.md#build-and-run-on-a-device-with-xcode)).

## Play

**Settings.** A screen before the game starts offers what the game supports: frame rate, render scale, docked or handheld mode, game language, the frame-rate counter and rumble. Everything is on one scrollable screen, grouped into **Game**, **Controls** and **Performance**, with menus, sliders and a reset to the settings the game was tested with. Tap **Play** to start; the app remembers your choices. What each setting does: [Settings](docs/settings.md).

**Touch controls.** Tap **2D** / **3D** at the top to switch layouts; the app remembers your choice. Wonder, Engage, Dread, 13 Sentinels, Link's Awakening, Ace Attorney Investigations Collection, Unicorn Overlord, Rhythm Heaven Groove, Octopath Traveler 0, Pokémon Legends: Z-A, Cuphead, Absolum, Brain Memory Training Academy, The Great Ace Attorney Chronicles, STEINS;GATE RE:BOOT, Big Brain Academy: Brain vs. Brain, Patrick's Parabox, Celeste, Raging Loop and Mario vs. Donkey Kong start in 2D, the other games in 3D (STEINS;GATE RE:BOOT's quick save is R3, in the 3D layout). In 3D, the right stick (the camera in most games) is not drawn: swipe on the right third of the screen, starting anywhere off the buttons. In Super Mario Galaxy and Super Mario Galaxy 2, other touches outside the controls move the pointer; in Captain Toad: Treasure Tracker they touch the game's screen (touch blocks, stun enemies), and in Big Brain Academy: Brain vs. Brain too (its menus and activities).
A connected game controller hides the touch controls and keeps every button.

**Rumble.** Game vibration uses the iPhone's haptic engine or a compatible connected controller. Controllers with separate left/right haptic outputs keep those effects separate. The launcher's **Game rumble** and **Rumble strength** settings control it independently of **Touch feedback**. Phone rumble approximates the Switch's effects; physical feel and controller compatibility still need device testing.

**Shaking.** Shake the iPhone to shake the controller, in games that read its motion: Super Mario Odyssey's motion moves (such as the cap throw on a shake) need it, and Odyssey only takes them in its default docked mode. A light bump does not count; a sharp flick of the phone does.

- **Game language** is English by default. Pick another when packing with `--language` (`-l`), by code or by name: `-l ja`, `-l zh-Hans`, `-l French` (`LANGUAGE` in Spyder). It must be one the game has; the script prints the game's languages and stops on one it lacks. To change it without rebuilding, pick another on the settings screen.
- **Saves and logs** are in the Files app, under the app's name: `save/` and `log.txt`. When something goes wrong, send `log.txt` (the previous run is `log.prev.txt`).
- **Short stutters** the first time a new scene appears are normal: the app compiles graphics for it once and remembers them for the next launch. What it remembered, and what the game's list names, is built before the game starts, behind "Preparing shaders" and a progress bar when that takes more than half a second.
- **Reinstalling:** some sideloading tools give a reinstalled app a new data folder. Copy `save/` and `pso_user.tsv` over from the old one to keep your progress.
- **Settings in a file:** lines like `DM_OPMODE=0` (handheld mode: lower resolution, higher frame rate) in `Documents/env.txt` win over the settings screen, which then shows them greyed out. `DM_FPS_TARGET=30` keeps Breath of the Wild, Tears of the Kingdom, Octopath Traveler 0 and Octopath Traveler II at their original 30 fps, which saves battery; `DM_PRESENT_INTERVAL=game` does the same for Monster Train 2. `DM_SHOW_FPS=1` shows the frame rate at the top left (`--show-fps` when packing turns it on from the start). `DM_LAUNCHER=0` skips the settings screen.

## Known issues

- No amiibo. Upstream games generally have no online features; this fork's tested Minecraft Microsoft login/cloud-save path is described above. Multiplayer remains unverified.
- Fire Emblem Engage: after switching away from the app and back, some sounds may stay silent until you restart it.
- Fire Emblem: Three Houses: small square patches on the ground where decals land.
- Super Mario Galaxy and Super Mario Galaxy 2: effects drawn as points or lines come out one pixel wide.
